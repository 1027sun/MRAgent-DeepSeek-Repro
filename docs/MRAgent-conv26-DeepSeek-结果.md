## 二、成本

| 项目 | 数值 |
| --- | --- |
| 主流程 API 调用 | 1,844 次 |
| 输入 tokens | 4,437,480（**缓存命中 60%**） |
| 输出 tokens | 1,322,724 |
| 主流程成本（低峰） | **$1.065** |
| Judge（152 次调用，估算） | 约 $0.10 |
| **合计** | **约 $1.17** |

比预估（$0.5–1）略高，超出的部分主要来自两处浪费：

1. **tag 打分调用被输出截断**（17 次）：某个 key 关联 200+ 个 tag，模型要输出全部评分，
   响应过长被截断，JSON 解析失败并重试 3 次，每次都白花 4 次调用。
2. **关键词 JSON 校验失败的兜底重试**：少量 session 需要多次重试。

低峰/高峰差一倍：北京时间工作日 09:00–12:00、14:00–18:00 是高峰，其余（含整个周末）半价。

## 三、这次真跑暴露出的 4 个 bug（已修）

静态读代码发现不了，都是跑起来才暴露的：

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | `agent.py` 调用 `check_key_json(..., replace=True)`，但 `schema.py` 里**没有这个参数** | 关键词连续 3 次校验失败时**直接崩溃** | 加 `replace` 参数并实现修复模式：丢弃非法条目，并把漏掉 `-n` 后缀的 id 做唯一前缀重映射 |
| 2 | 模型生成退化，改写出**扁平对象**而不是 `{sentence:[...]}` 结构 | `embed_sample` 对 None 迭代崩溃 | 三处加防御：`embed_sample` 跳过该记录、`add_topics` 容忍 None、`personal_sentences` 容忍 None |
| 3 | `question_keys["keywords"]` 可能是 `null` | 整道题丢失（question51） | `answer_question` 与 `set_queried_keywords` 加空值兜底 |
| 4 | `run.py` 按**文件是否存在**跳过整个改写阶段 | 按 session 续跑的逻辑根本没被调用，坏 session 无法单独重生成 | 改为始终调用 `rewrite_sample`（它内部按 session 续跑） |

其中 #1、#2、#3 是**仓库原有的问题**，#4 是我改造时留下的缺口。

## 四、几个必要的说明

**这个分数不能直接和论文比。** 原因有四个：

1. 只跑了**一段**对话（conv-26，152 道计分题），论文是 10 段对话的汇总（1986 题）
2. Judge 用 `deepseek-v4-pro`，论文用 `gpt-4o-mini`
3. Embedding 换成 `bge-base-en-v1.5`，论文用 `text-embedding-3-large`
4. 论文是 3 次独立重复取均值

论文 Table 1（Gemini backbone）的 MRAgent 是：多跳 75.17 / 时间 80.37 / 开放域 68.75 / 单跳 90.48，总体 84.21。
本次在**这一段对话**上普遍略高，但样本不同，只能说明流程正确、效果在同一量级，不能说明优于论文。

**Judge 的 token 没有被记账。** `eval/judge.py` 用的是自己的 client，不经过 `llm/controller.py`
的记账钩子，所以 `token_usage.jsonl` 里只有主流程的用量，judge 那部分是按调用次数估算的。
想精确统计的话，需要给 judge 也接上记账。

## 五、下一步

1. **对比臂**：Passive（复用同一套记忆缓存，去掉工具循环、一次 top-k 直接答题）和
   Full-context（整段对话塞进 prompt）。两条臂都能复用已建好的记忆，边际成本各约 $0.1。
2. **建议先修 tag 打分截断**，否则每次 MRAgent 跑都会浪费约 10% 的调用量。
3. 想跑更多对话的话，优先补 `conv-42`（260 题、题型五类齐全）或直接上全量（约 $10–15）。
